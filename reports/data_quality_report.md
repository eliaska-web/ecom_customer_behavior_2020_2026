## 2. Единица наблюдения и ключи
- customers: строка = клиент, ключ `customer_id` (уникальность: **подтверждена**)

- product_summary: строка = продукт, ключ (`category`, `product_name`) (уникальность: **подтверждена**)
- monthly_revenue: строка = месяц, ключ (`year`, `month`) (уникальность: **подтверждена**)

## 3. Структура и типы
- registration_date, order_date, delivery_date конвертированы в datetime (шаг 15): NaT = 0 во всех трёх полях
- Диапазоны: registration_date 2011-08-03 … 2026-04-01; order_date 2020-01-01 … 2026-03-30; delivery_date 2020-01-03 … 2026-04-12
- Бизнес-правило «delivery_date ≥ order_date»: нарушений 0
- Остальные типы соответствуют смыслу полей

## 4. Пропуски и полнота
- `orders.customer_rating`: 15 749 NaN (63,0% строк orders)
- Причина: рейтинг существует только у заказов со статусом `Delivered` (45,1% от всех Delivered, 0% у остальных статусов)
- Распределение статусов: Delivered = 20 497, Returned = 2 020, Cancelled = 1 456, Processing = 1 027
- Стратегия: **не импутовать**; оставить NaN + добавить флаг `has_rating` (шаг 11)
- В остальных таблицах пропусков нет

## 5. Дубликаты и уникальность

- Дубликатов по ключам: 0 (проверено)

- age 18–75: распределение нормальное, пик ~35 лет, аномалий нет

## 7. Временное покрытие
- orders: 2020-01 … 2026-03 (75 месяцев, полное покрытие)
- monthly_revenue: 2020-01 … 2026-03 (75 месяцев)
- **Периоды совпадают полностью**: все месяцы orders присутствуют в monthly_revenue и наоборот
- Все 25 000 заказов orders.csv попадают в покрытие monthly_revenue
- `registration_date`: 2011-08-03 … 2026-04-01 — шире периода заказов (2020-01 … 2026-03)
191 клиент зарегистрирован до 2020-01, поэтому `sum(monthly_revenue.new_customers)` = 7 284 < 8 000
**Проверка гипотез о природе `new_customers` (первый заказ в месяце):**
- Гипотеза (а) «первый заказ любого статуса» — опровергнута (0 совпадений из 75).
- Гипотеза (б) «первый Delivered-заказ» — опровергнута (0 совпадений из 75).
Значения `monthly_revenue.new_customers` систематически ниже (в 2,5–3 раза), чем количество клиентов с первым заказом по `orders.csv`.

## 8. Межтабличная целостность
- `monthly_revenue.return_rate = 0,0` во всех 75 строках при `orders.returned = 8,08%` → поле **непригодно**; источник истины по возвратам — `orders.returned`
- `monthly_revenue` агрегирует **только заказы со статусом Delivered** (подтверждено):
- `sum(monthly_revenue.orders)` = 20 497 = количество заказов со статусом Delivered в orders.csv
  - `sum(monthly_revenue.revenue_usd)` = 2 585 126.5 = выручка по заказам со статусом Delivered в orders.csv
  - Заказы со статусами Returned (2 020), Cancelled (1 456), Processing (1 027) не включены в агрегат
- Для точных расчётов по всем заказам использовать `orders.csv`; `monthly_revenue` применять только для динамики Delivered-выручки
- **Природа пропусков `customer_rating`** (15 749 NaN):
  - Рейтинг существует только у заказов со статусом `Delivered`
  - Среди Delivered рейтинг получили ~45% заказов
  - У статусов Cancelled, Processing, Returned рейтинга нет
  - Это содержательный пропуск (оценка не поставлена), не ошибка сбора
- `product_summary` агрегирует **все заказы кроме статуса Cancelled** (подтверждено):
  - `sum(product_summary.total_orders)` = 23 544 = 25 000 − 1 456 (Cancelled)
  - `sum(product_summary.total_revenue_usd)` = выручка по всем заказам кроме Cancelled
  - Для анализа продуктов использовать `product_summary`; для анализа всех статусов — агрегировать `orders.csv`
- new_customers vs регистрации: гипотеза опровергнута, факты и разрыв 525 — см. раздел 7
- Агрегатные поля `customers` не согласованы с `orders.csv` за период 2020-2026:
  sum(total_orders) = 132 362 vs 25 000 заказов; sum(total_spend_usd) = 12 469 138,80 vs 3 136 404,66;
  days_since_last_purchase max = 582 vs recency max = 2 281 день; total_orders min = 1 при 337 клиентах без заказов
  Гипотезы: (а) поля описывают lifetime вне окна orders.csv; (б) несогласованность синтетической генерации
  Решение: для анализа периода 2020-2026 использовать метрики из orders (RFM); поля total_orders /
  total_spend_usd / days_since_last_purchase считать lifetime-полями с неподтверждённым определением
- **Природа поля `monthly_revenue.new_customers`:**
Поле не отражает ни регистрации, ни первые заказы (любого статуса или только Delivered) в рамках месяца. Расхождение с `orders.csv` объясняется либо синтетической природой датасета (случайная генерация / скрытые фильтры), либо тем, что `monthly_revenue` учитывает исторические заказы до 2020 года, которые отсутствуют в таблице `orders`. Поле признано невалидным для аналитики.

## 10. Риски для анализа
- `product_summary` пригодна для продуктовых метрик только с явной оговоркой «агрегат исключает Cancelled» (~6% заказов)
- Использование customers.total_orders / total_spend_usd / days_since_last_purchase как метрик периода 2020-2026 даст кратные расхождения с orders.csv (см. раздел 8)
- `monthly_revenue.new_customers` **категорически нельзя использовать** для расчета метрик привлечения (Acquisition), конверсий, когортного анализа и оценки доли New vs Returning. Использование поля даст критически искаженные результаты (занижение в ~3 раза).
- JOIN orders и monthly_revenue по месяцам требует учёта: monthly_revenue агрегирует только Delivered; product_summary агрегирует все кроме Cancelled
- Для когортного анализа retention использовать orders.csv, а не monthly_revenue.new_customers (определение поля не подтверждено, см. разделы 7–8)
- Импутация customer_rating исказит статистику рейтинга

## 13. RFM-анализ клиентов

### Методология
- Recency (R): дней с последней покупки (snapshot_date = max(order_date) + 1 день)
- Frequency (F): количество заказов
- Monetary (M): сумма покупок в USD
- Скоринг: квантильное разбиение на 5 групп (1-5) с обработкой дубликатов границ
- Сегментация: правила на основе R, F, M scores

### Результаты
- Проанализировано клиентов: 7 663 из 8 000 (337 клиентов без заказов в периоде)
- Распределение по сегментам:
  - Loyal Customers: ~69.2% выручки
  - At Risk: ~24.0% выручки
  - Regular: ~6.8% выручки
  - Champions, New Customers, Lost: не выявлены в значимых количествах

### Ограничения
- RFM не учитывает сезонность покупок
- Snapshot date выбран как max(order_date) + 1 день, что может смещать recency для старых клиентов
- 337 клиентов (4.2%) не имеют заказов в периоде 2020-2026

## 14. ABC-XYZ анализ товаров

### Методология
- ABC: кумулятивная доля выручки (A ≤ 80%, B ≤ 95%, C — остальное)
- XYZ: коэффициент вариации месячного спроса (X ≤ 0.10, Y ≤ 0.25, Z > 0.25)

### Результаты
- ABC распределение: A = 62 товара, B = 49 товаров, C = 29 товаров
- Группа A формирует 79.7% выручки (соответствует критерию ~80%)
- XYZ распределение: все 140 товаров (100%) в группе Z

### Критическое наблюдение
**Все товары попали в группу Z (нестабильный спрос)**. Это может быть следствием:
- Синтетической природы данных (случайное распределение заказов)
- Короткого периода наблюдения для некоторых товаров
- Высокой волатильности спроса в e-commerce

### Ограничения
- XYZ-анализ на месячном уровне может быть слишком агрегированным для 140 товаров
- Для товаров с низким объёмом продаж CV искусственно завышен
- Отсутствие товаров в группах X и Y ограничивает применимость матрицы ABC-XYZ для управления запасами
